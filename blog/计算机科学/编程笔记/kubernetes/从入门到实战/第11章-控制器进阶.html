11.1 DaemonSet

11.1.1 DaemonSet 核心概念

DaemonSet 是一种确保每个 Node 上运行一个 Pod 的控制器。当新节点加入集群时，DaemonSet 会自动在新节点上部署 Pod；当节点移除时，对应的 Pod 也会被删除。

│  │   Node-1      │  │   Node-2      │  │   Node-3      │ │
│  │  ┌──────────┐ │  │  ┌──────────┐ │  │  ┌──────────┐ │ │

│  │  └──────────┘ │  │  └──────────┘ │  │  └──────────┘ │ │
│  │  ┌──────────┐ │  │  ┌──────────┐ │  │  ┌──────────┐ │ │

└─────────────────────────────────────────────────────────┘

11.1.2 典型应用场景

场景 说明 示例
日志收集 每个节点部署日志采集 Agent Fluentd、Fluent Bit、Logstash
监控 Agent 每个节点采集系统指标 Node Exporter、Datadog Agent

11.1.3 DaemonSet YAML 结构详解

完整 YAML 配置示例

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
  namespace: kube-system
  labels:
    app: fluentd
    tier: logging
  annotations:
    description: "Fluentd 日志收集 DaemonSet"

spec:
  # 标签选择器（必填，不可修改）
  selector:
    matchLabels:
      app: fluentd
      tier: logging

  # 更新策略
  updateStrategy:
    type: RollingUpdate          # 更新类型：RollingUpdate / OnDelete
    rollingUpdate:
      maxUnavailable: 1          # 最大不可用 Pod 数

  # 历史版本保留
  revisionHistoryLimit: 10

  # Pod 模板
  template:
    metadata:
      labels:
        app: fluentd
        tier: logging
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "24231"

    spec:
      # ========== 节点选择 ==========
      # 方式一：nodeSelector（简单匹配）
      nodeSelector:
        kubernetes.io/os: linux
        logging-enabled: "true"

      # 方式二：nodeAffinity（复杂匹配，推荐）
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: kubernetes.io/os
                    operator: In
                    values:
                      - linux
                  - key: node-type
                    operator: In
                    values:
                      - worker
                      - general
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              preference:
                matchExpressions:
                  - key: kubernetes.io/hostname
                    operator: In
                    values:
                      - node-1
                      - node-2

      # 污点容忍（允许调度到有污点的节点）
      tolerations:
        - key: node-role.kubernetes.io/master
          operator: Exists
          effect: NoSchedule
        - key: dedicated
          operator: Equal
          value: logging
          effect: NoSchedule

      # 服务账户
      serviceAccountName: fluentd
      serviceAccount: fluentd

      # 容器定义
      containers:
        - name: fluentd
          image: fluent/fluentd:v1.16-alpine
          imagePullPolicy: IfNotPresent

          # 端口声明
          ports:
            - name: http
              containerPort: 24231
              protocol: TCP

          # 环境变量
          env:
            - name: FLUENTD_CONF
              value: "fluent.conf"
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName

          # 资源限制
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

          # 健康检查
          livenessProbe:
            httpGet:
              path: /health
              port: 24231
            initialDelaySeconds: 30
            periodSeconds: 30
            failureThreshold: 3

          readinessProbe:
            httpGet:
              path: /health
              port: 24231
            initialDelaySeconds: 10
            periodSeconds: 10
            failureThreshold: 3

          # 卷挂载
          volumeMounts:
            - name: varlog
              mountPath: /var/log
              readOnly: true
            - name: varlibdockercontainers
              mountPath: /var/lib/docker/containers
              readOnly: true
            - name: fluentd-config
              mountPath: /fluentd/etc
            - name: fluentd-buffer
              mountPath: /fluentd/buffer

          # 安全上下文
          securityContext:
            privileged: true
            readOnlyRootFilesystem: false

      # 卷定义
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
        - name: varlibdockercontainers
          hostPath:
            path: /var/lib/docker/containers
        - name: fluentd-config
          configMap:
            name: fluentd-config
        - name: fluentd-buffer
          hostPath:
            path: /var/lib/fluentd/buffer

      # 优先级
      priorityClassName: system-node-critical

11.1.4 nodeSelector 与 nodeAffinity 对比

特性 nodeSelector nodeAffinity
匹配方式 精确匹配（key=value） 支持多种操作符（In, NotIn, Exists, DoesNotExist）
复杂条件 不支持 支持多个条件组合（AND/OR）
软/硬约束 仅硬约束 支持硬约束（required）和软约束（preferred）
推荐程度 简单场景 所有场景（推荐） 
# nodeSelector 示例
nodeSelector:
  kubernetes.io/os: linux
  logging-enabled: "true"

# nodeAffinity 示例（等效的复杂版本）
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/os
              operator: In
              values: ["linux"]
            - key: logging-enabled
              operator: In
              values: ["true"]

11.2 StatefulSet

11.2.1 StatefulSet 核心概念

StatefulSet 是为有状态应用设计的控制器，提供稳定的标识、有序的部署和稳定的存储。

┌─────────────────────────────────────────────────────────────┐
│                    StatefulSet vs Deployment                   │
│                                                               │
│  Deployment（无状态）:                                        │
│  ┌────────┐  ┌────────┐  ┌────────┐                         │
│  │ Pod-A  │  │ Pod-B  │  │ Pod-C  │  ← Pod 名称随机           │
│  │ 不稳定 │  │ 不稳定 │  │ 不稳定 │  ← Pod IP 不稳定          │
│  └────────┘  └────────┘  └────────┘                         │
│  特点：可以任意替换，不需要关心顺序                             │
│                                                               │
│  StatefulSet（有状态）:                                       │
│  ┌────────┐  ┌────────┐  ┌────────┐                         │
│  │ web-0  │  │ web-1  │  │ web-2  │  ← Pod 名称固定有序      │
│  │ 稳定  │  │ 稳定  │  │ 稳定  │  ← Pod IP 稳定              │
│  └────────┘  └────────┘  └────────┘                         │
│  特点：有序部署/删除，稳定存储绑定                             │
└─────────────────────────────────────────────────────────────┘

11.2.2 StatefulSet 三大特性

特性 说明 实现方式
稳定标识 Pod 名称有序且固定（web-0, web-1, web-2） 基于序号的命名规则
有序部署/删除 按顺序逐个创建/删除 Pod 序号控制（N-1 → 0）
稳定存储 每个 Pod 绑定独立的持久存储 volumeClaimTemplates

11.2.3 与 Deployment 的核心区别

维度 Deployment StatefulSet
Pod 名称 随机后缀（nginx-7d4f5b6c8-xxxxx） 固定序号（web-0, web-1, web-2）
部署顺序 并行创建所有 Pod 按序号顺序创建（0 → N-1）
删除顺序 并行删除所有 Pod 按序号逆序删除（N-1 → 0）
存储绑定 共享存储或无存储 每个 Pod 独立存储绑定
网络标识 不稳定 稳定 DNS 名称（web-0.svc-name）
更新策略 滚动更新 可滚动或按序更新
适用场景 无状态应用 有状态应用（数据库、集群）

11.2.4 典型应用场景

应用 说明
MySQL 集群 需要主从复制，每个实例角色固定
Redis Cluster 需要稳定的节点标识和数据持久化
ZooKeeper 需要有序的节点身份
Kafka 需要稳定的 Broker ID 和日志存储
etcd 集群 每个节点有固定的 peer URL
MongoDB 副本集 需要稳定的节点名称

11.2.5 StatefulSet YAML 结构详解

完整 YAML 配置示例（以 Redis Cluster 为例）

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis-cluster
  namespace: default
  labels:
    app: redis-cluster
    tier: cache
  annotations:
    description: "Redis Cluster StatefulSet"

spec:
  # Pod 数量
  replicas: 6                    # Redis Cluster 推荐 6 个节点（3主3从）

  # 标签选择器（必填，不可修改）
  selector:
    matchLabels:
      app: redis-cluster

  # 服务名称（必须匹配一个 Headless Service）
  serviceName: redis-cluster-service  # 关联的无头服务

  # 更新策略
  updateStrategy:
    type: RollingUpdate          # RollingUpdate / OnDelete
    rollingUpdate:
      partition: 0               # 从第几个 Pod 开始更新（用于灰度）

  # 历史版本保留
  revisionHistoryLimit: 10

  # Pod 模板
  template:

11.3 Job

11.3.1 Job 核心概念

Job 用于执行一次性任务，确保指定数量的 Pod 成功完成后结束。与 Deployment 不同，Job 关注的是"任务完成"而不是"持续运行"。

┌─────────────────────────────────────────────────────────┐
│                      Job 工作流程                         │
│                                                           │
│  1. 创建 Job                                              │
│     ↓                                                     │
│  2. 创建 Pod 执行任务                                     │
│     ↓                                                     │
│  3. 监控 Pod 运行状态                                     │
│     ├── Pod 成功 → 标记完成                               │
│     ├── Pod 失败 → 重新创建（取决于 backoffLimit）         │
│     └── Pod 超时 → 重新创建                               │
│     ↓                                                     │
│  4. 所有 Pod 完成 → Job 状态为 Complete                   │
│     ↓                                                     │
│  5. 成功的 Pod 保留（便于排查）                           │
│                                                           │
│  关键参数：                                               │
│  ├── completions: 需要多少个 Pod 成功完成                 │
│  ├── parallelism: 同时运行多少个 Pod                      │
│  └── backoffLimit: 失败后最多重试次数                     │
└─────────────────────────────────────────────────────────┘

11.3.2 Job YAML 结构详解

完整 YAML 配置示例

apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
  namespace: default
  labels:
    app: data-migration
    tier: batch
  annotations:
    description: "一次性数据迁移任务"

spec:
  # 完成所需的 Pod 数量（默认 1）
  completions: 4

  # 并行运行的 Pod 数量（默认 1）
  parallelism: 2

  # 失败后最多重试次数（默认 6）
  backoffLimit: 3

  # 活动截止时间（超过则标记失败）
  activeDeadlineSeconds: 1800     # 30 分钟

  # TTL（完成后自动清理，Kubernetes 1.12+）
  ttlSecondsAfterFinished: 3600   # 完成后 1 小时自动删除

  # 选择器
  selector:
    matchLabels:
      app: data-migration

  # 手动选择 Pod（用于控制并行执行）
  manualSelector: false

  # Pod 模板
  template:
    metadata:
      labels:
        app: data-migration
    spec:
      # 重启策略（Job 必须是 OnFailure 或 Never）
      restartPolicy: OnFailure

      containers:
        - name: migration
          image: postgres:16-alpine
          command:
            - sh
            - -c
            - |
              echo "开始数据迁移任务..."
              echo "Pod 名称: ${POD_NAME}"
              echo "处理分片: ${JOB_COMPLETION_INDEX}"

              # 模拟数据迁移
              pg_dump -h ${DB_HOST} -U ${DB_USER} ${DB_NAME} | \
                psql -h ${TARGET_HOST} -U ${TARGET_USER} ${TARGET_NAME}

              echo "数据迁移完成"
          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: JOB_COMPLETION_INDEX
              valueFrom:
                fieldRef:
                  fieldPath: metadata.annotations['batch.kubernetes.io/job-completion-index']
            - name: DB_HOST
              value: "source-db.default.svc.cluster.local"
            - name: DB_USER
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: username
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password

          resources:
            requests:
              cpu: "200m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "1Gi"

          volumeMounts:
            - name: migration-scripts
              mountPath: /scripts
            - name: temp-data
              mountPath: /tmp/data

      volumes:
        - name: migration-scripts
          configMap:
            name: migration-scripts
        - name: temp-data
          emptyDir: {}

      # 亲和性
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              preference:
                matchExpressions:
                  - key: workload
                    operator: In
                    values:
                      - batch

11.3.3 Job 参数详解

参数 类型 默认值 说明
spec.completions integer 1 需要成功完成的 Pod 总数
spec.parallelism integer 1 同时运行的 Pod 数量
spec.backoffLimit integer 6 失败后最多重试次数
spec.activeDeadlineSeconds integer nil 活动截止时间（秒）
spec.ttlSecondsAfterFinished integer nil 完成后自动清理时间
spec.selector object - 标签选择器
spec.manualSelector boolean false 是否手动选择 Pod

completions 与 parallelism 的关系

场景 1：completions=1, parallelism=1
  → 顺序执行 1 个 Pod，完成即结束

场景 2：completions=3, parallelism=1
  → 顺序执行 3 个 Pod（第 1 个完成后启动第 2 个）

场景 3：completions=3, parallelism=3
  → 并行执行 3 个 Pod，全部完成即结束

场景 4：completions=1, parallelism=3
  → 同时启动 3 个 Pod，任意 1 个成功即结束（其他 Pod 被终止）

场景 5：completions=4, parallelism=2
  → 先启动 2 个 Pod，完成 1 个后补 1 个，直到 4 个完成

11.4 CronJob

11.4.1 CronJob 核心概念

CronJob 基于 cron 表达式定时执行 Job。每次调度时，CronJob 会创建一个新的 Job，由 Job 来管理 Pod 的执行。

┌─────────────────────────────────────────────────────────────┐
│                      CronJob 工作流程                         │
│                                                               │
│  CronJob (定时触发器)                                         │
│  │                                                            │
│  │  schedule: "0 2 * * *"  ← 每天凌晨 2 点                    │
│  │  concurrencyPolicy: Allow                                  │
│  │  successfulJobsHistoryLimit: 3                             │
│  │  failedJobsHistoryLimit: 1                                 │
│  │                                                            │
│  ├──T1──→ Job-1 → Pod-1 → 执行 → 成功 ✓                      │
│  ├──T2──→ Job-2 → Pod-2 → 执行 → 成功 ✓                      │
│  ├──T3──→ Job-3 → Pod-3 → 执行 → 失败 ✗ (保留)               │
│  └──T4──→ Job-4 → Pod-4 → 执行 → 运行中...                   │
│                                                               │
│  历史记录：                                                   │
│  ├── 成功的 Job 保留 3 个（successfulJobsHistoryLimit）       │
│  └── 失败的 Job 保留 1 个（failedJobsHistoryLimit）           │
└─────────────────────────────────────────────────────────────┘

11.4.2 schedule 语法

CronJob 的 schedule 语法与 Linux crontab 相同，由 5 个字段组成。

┌──────────────── 分钟 (0 - 59)
│ ┌────────────── 小时 (0 - 23)
│ │ ┌──────────── 日 (1 - 31)
│ │ │ ┌────────── 月 (1 - 12)
│ │ │ │ ┌──────── 星期 (0 - 6, 0 = 周日)
│ │ │ │ │
* * * * *   ← 每分钟执行一次

常用时间表达式

表达式 含义
* * * * * 每分钟
*/5 * * * * 每 5 分钟
0 * * * * 每小时整点
0 */2 * * * 每 2 小时
0 2 * * * 每天凌晨 2 点
0 2 * * 0 每周日凌晨 2 点
0 2 1 * * 每月 1 号凌晨 2 点
0 9-17 * * 1-5 工作日 9-17 整点
30 3 * * 1,15 每月 1 号和 15 号凌晨 3:30

11.4.3 concurrencyPolicy 策略

策略 说明
Allow 允许多个 Job 同时运行（默认）
Forbid 不允许并发，跳过本次调度
Replace 如果上一个 Job 仍在运行，用新 Job 替换它 
场景：CronJob 每 10 分钟执行一次，任务需要 15 分钟完成

Allow:   Job-1 运行中 → Job-2 启动 → 两个并发运行
Forbid:  Job-1 运行中 → Job-2 被跳过 → 仅 Job-1 运行
Replace: Job-1 运行中 → Job-1 被终止 → Job-2 替代运行

11.4.4 CronJob YAML 结构详解

完整 YAML 配置示例（MySQL 备份）

apiVersion: batch/v1
kind: CronJob
metadata:
  name: mysql-backup
  namespace: default
  labels:
    app: mysql-backup
    tier: maintenance
  annotations:
    description: "MySQL 定时备份 CronJob"

spec:
  # 调度时间（每天凌晨 2:30 执行）
  schedule: "30 2 * * *"

  # 并发策略
  concurrencyPolicy: Forbid       # 不允许并发，避免备份冲突

  # 起始截止时间（可选）
  startingDeadlineSeconds: 300    # 错过了调度时间 5 分钟则跳过

  # 历史记录保留
  successfulJobsHistoryLimit: 3   # 保留最近 3 个成功的 Job
  failedJobsHistoryLimit: 1       # 保留最近 1 个失败的 Job

  # 暂停调度（可用于临时禁用）
  suspend: false                  # true 时暂停所有调度

  # Job 模板（与 Job spec 相同）
  jobTemplate:
    spec:
      # Job 级别的配置
      backoffLimit: 2
      activeDeadlineSeconds: 1200  # 单次备份最多 20 分钟
      ttlSecondsAfterFinished: 86400  # 完成后 1 天自动清理

      # 完成条件
      completions: 1
      parallelism: 1

      # Pod 模板
      template:
        metadata:
          labels:
            app: mysql-backup
        spec:
          restartPolicy: OnFailure

          containers:
            - name: backup
              image: mysql:8.0
              command:
                - sh
                - -c
                - |
                  set -e
                  echo "开始 MySQL 备份: $(date)"

                  BACKUP_FILE="/backup/mysql-full-backup-$(date +%Y%m%d-%H%M%S).sql.gz"

                  # 执行全量备份
                  mysqldump \
                    -h ${MYSQL_HOST} \
                    -u ${MYSQL_USER} \
                    -p${MYSQL_PASSWORD} \
                    --all-databases \
                    --single-transaction \
                    --routines \
                    --triggers \
                    --events \
                    | gzip > ${BACKUP_FILE}

                  echo "备份完成: ${BACKUP_FILE} ($(du -h ${BACKUP_FILE} | cut -f1))"

                  # 上传到对象存储（可选）
                  if [ -n "${S3_BUCKET}" ]; then
                    echo "上传备份到 S3..."
                    aws s3 cp ${BACKUP_FILE} s3://${S3_BUCKET}/mysql-backups/
                  fi

                  echo "备份任务成功完成"

              env:
                - name: MYSQL_HOST
                  value: "mysql-primary.default.svc.cluster.local"
                - name: MYSQL_USER
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: username
                - name: MYSQL_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: password
                - name: S3_BUCKET
                  value: "my-backup-bucket"

              resources:
                requests:
                  cpu: "200m"
                  memory: "256Mi"
                limits:
                  cpu: "1000m"
                  memory: "1Gi"

              volumeMounts:
                - name: backup-storage
                  mountPath: /backup

          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backup-pvc

11.5 控制器选择指南

11.5.1 控制器选择决策树

你的应用是什么类型？
│
├── 需要在每个节点上运行？
│   └── 是 → DaemonSet
│

│
└── 无状态应用（常规 Web/API 服务）？
    └── Deployment

  name: migration-scripts

  migrate.sh: |
    #!/bin/bash
    set -e

    echo "========================================"
    echo " 数据迁移脚本"
    echo " 时间: $(date)"
    echo " Pod: ${POD_NAME}"
    echo " 分片: ${JOB_COMPLETION_INDEX}"

    # 建表
    echo "创建表结构..."
    psql -h ${DB_HOST} -U ${DB_USER} ${DB_NAME} << SQL
    CREATE TABLE IF NOT EXISTS users (
      id SERIAL PRIMARY KEY,
      username VARCHAR(50) NOT NULL,
      email VARCHAR(100) NOT NULL,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );

    CREATE TABLE IF NOT EXISTS orders (
      id SERIAL PRIMARY KEY,
      user_id INTEGER REFERENCES users(id),
      amount DECIMAL(10,2) NOT NULL,
      status VARCHAR(20) DEFAULT 'pending',
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );
    SQL

    # 导入数据（每个分片处理不同范围）
    echo "导入分片 ${JOB_COMPLETION_INDEX} 的数据..."
    OFFSET=$((JOB_COMPLETION_INDEX * 2500))

    psql -h ${DB_HOST} -U ${DB_USER} ${DB_NAME} << SQL
    INSERT INTO users (username, email)
    SELECT 
      'user_' || i,
      'user_' || i || '@example.com'
    FROM generate_series(${OFFSET}, ${OFFSET} + 2499) AS i;

    INSERT INTO orders (user_id, amount, status)
    SELECT 
      (SELECT id FROM users ORDER BY random() LIMIT 1),
      (random() * 1000)::decimal(10,2),
      (ARRAY['pending', 'completed', 'cancelled'])[1 + floor(random() * 3)]
    FROM generate_series(1, 1000) AS i;
    SQL

    echo "分片 ${JOB_COMPLETION_INDEX} 迁移完成"
    echo "完成时间: $(date)"
EOF

  name: mysql-backup
  labels:
    app: mysql-backup
    tier: maintenance
  annotations:
    description: "每天凌晨 2:30 备份 MySQL 数据库"
spec:
  schedule: "30 2 * * *"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  suspend: false
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 1200
      ttlSecondsAfterFinished: 86400
      template:
        metadata:
          labels:
            app: mysql-backup
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: mysql:8.0
              command:
                - sh
                - -c
                - |
                  set -e
                  BACKUP_DIR="/backup"
                  TIMESTAMP=$(date +%Y%m%d-%H%M%S)
                  BACKUP_FILE="${BACKUP_DIR}/mysql-backup-${TIMESTAMP}.sql.gz"

                  echo "[$(date)] 开始 MySQL 全量备份"

                  PGPASSWORD="${MYSQL_PASSWORD}"
                  mysqldump \
                    -h ${MYSQL_HOST} \
                    -u ${MYSQL_USER} \
                    --all-databases \
                    --single-transaction \
                    --routines \
                    --triggers \
                    --events \
                    --set-gtid-purged=OFF \
                    2>/dev/null | gzip > ${BACKUP_FILE}

                  BACKUP_SIZE=$(du -h ${BACKUP_FILE} | cut -f1)
                  echo "[$(date)] 备份完成: ${BACKUP_FILE} (${BACKUP_SIZE})"

                  # 清理 3 天前的备份
                  find ${BACKUP_DIR} -name "*.sql.gz" -mtime +3 -delete 2>/dev/null
                  echo "[$(date)] 旧备份清理完成"
                  echo "[$(date)] 备份任务成功"

              env:
                - name: MYSQL_HOST
                  value: "mysql-primary.default.svc.cluster.local"
                - name: MYSQL_USER
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: username
                - name: MYSQL_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: mysql-credentials
                      key: password
              resources:
                requests:
                  cpu: "200m"
                  memory: "256Mi"
                limits:
                  cpu: "1000m"
                  memory: "1Gi"
              volumeMounts:
                - name: backup-storage
                  mountPath: /backup
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: backup-pvc
          affinity:
            nodeAffinity:
              preferredDuringSchedulingIgnoredDuringExecution:

11.8 章节小结

核心概念总结

  1. DaemonSet：每个 Node 运行一个 Pod，适用于节点级代理（日志、监控、网络）
  2. StatefulSet：有状态应用控制器，提供稳定标识、有序部署、稳定存储
  3. Job：一次性任务控制器，支持并行执行（parallelism / completions）
  4. CronJob：定时任务控制器，基于 cron 表达式调度 Job

一次性批处理 Job parallelism / completions
定时周期任务 CronJob schedule / concurrencyPolicy

最佳实践

  • DaemonSet：使用 nodeSelector / nodeAffinity 精确控制节点范围，配合 tolerations 处理污点节点
  • StatefulSet：务必配置 volumeClaimTemplates 实现数据持久化，使用 Headless Service 提供稳定 DNS
  • Job：合理设置 backoffLimit 和 activeDeadlineSeconds，使用 ttlSecondsAfterFinished 自动清理
  • CronJob：使用 concurrencyPolicy: Forbid 避免并发冲突，保留足够的历史记录用于排查
  • 通用：所有控制器配置合理的资源限制、健康检查和 Pod 标签，便于监控和管理
